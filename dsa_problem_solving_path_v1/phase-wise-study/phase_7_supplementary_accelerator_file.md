# 4. Mock execution script

Use this script in every serious mock:
1. Restate the problem.
2. Ask 2-4 clarifying questions.
3. State the brute-force baseline.
4. Identify the optimized pattern.
5. Explain the invariant or state.
6. Walk a tiny example.
7. Code in a structured way.
8. Test obvious edge cases.
9. State time and space complexity.
10. Reflect on one improvement.

This script prevents chaotic performance.

# 5. Daily accelerator plan

## Day A — Arrays and strings
Focus on:
- two pointers
- sliding window
- indexing discipline
- substring logic

Execution goals:
- solve under time
- narrate invariants clearly
- avoid off-by-one bugs

Verbal checkpoint:
- “My invariant is ____, and that tells me when the pointers move.”

## Day B — Trees and graphs
Focus on:
- BFS vs DFS choice
- recursion clarity
- visited semantics
- graph state tracking

Execution goals:
- explain traversal choice early
- state what visited means
- test structural edge cases

Verbal checkpoint:
- “I’m using BFS/DFS because the main goal is ____ and my state is ____.”

## Day C — DP and optimization
Focus on:
- state definition
- recurrence
- base cases
- fill order or memo logic

Execution goals:
- define `dp[state]` precisely
- test the recurrence on a tiny input
- avoid saying “it feels like DP” without formalizing it

Verbal checkpoint:
- “`dp[state]` means ____, and the transition is ____.”

## Day D — Mixed mock
Focus on:
- fast classification
- emotional control
- recovery when the first approach fails
- adapting to follow-ups

Execution goals:
- compare two approaches before coding
- recover out loud if stuck
- keep narration structured even after a mistake

Verbal checkpoint:
- “The baseline is ____, but the constraint pressure suggests ____ instead.”

## Day E — Weakness diagnosis
Focus on:
- recurring bugs
- slow pattern recognition
- weak explanations
- shaky complexity summaries

Execution goals:
- write your top three failure modes
- patch each one with one focused drill
- stop doing random problems with no diagnosis plan

Verbal checkpoint:
- “My actual bottleneck is not topic knowledge; it is ____.”

## Day F — Optional final drills
Focus on:
- short timed reps
- confidence stabilization
- concise explanations
- calm pacing

Execution goals:
- keep it light
- avoid learning brand-new heavy topics
- finish the week mentally fresh

# 6. Weakness diagnosis sheet

Use this after every mock.

| Category | Ask yourself |
|---|---|
| Clarification | Did I ask enough before coding? |
| Pattern choice | Did I identify the right family fast enough? |
| Explanation | Did my narration stay structured? |
| Coding | Were bugs mostly logic, syntax, or boundary-related? |
| Testing | Did I catch edge cases independently? |
| Complexity | Did I clearly state time and space? |
| Follow-up | Did I adapt well after changes? |

A short written diagnosis is better than vague frustration.

---

# 7. High-frequency interview mistakes

## Clarification mistakes
- coding before understanding constraints
- assuming sortedness, uniqueness, or mutability without asking

## Communication mistakes
- long silence
- jumping straight to code
- explaining too late instead of explaining while deciding

## Coding mistakes
- off-by-one errors
- null/empty handling gaps
- mutable state bugs in recursion or graph traversal
- forgetting helper invariants

## Testing mistakes
- only testing the happy path
- ignoring empty inputs, duplicates, boundaries, or single-element cases

## Closing mistakes
- forgetting complexity
- ending without summarizing trade-offs
- failing to answer the interviewer’s follow-up directly

# 8. Recovery playbook

If you are stuck, say something like:
1. “Let me step back and state the brute-force approach.”
2. “That would be too slow because ____.”
3. “The useful structure here seems to be ____.”
4. “I’ll try a smaller example to validate that.”

This sounds far stronger than silent panic.

# 10. 60-second drills

Practice answering these aloud:
- How do you usually start solving a new interview problem?
- When do you choose BFS over DFS?
- How do you explain a sliding-window invariant?
- How do you define DP state clearly?
- What do you do when your first solution is too slow?
- How do you test a solution before saying you are done?

If these are slow or fuzzy, fix the explanation skill directly.
